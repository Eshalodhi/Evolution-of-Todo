# TODO App Constitution - INTERMEDIATE Level

A command-line todo application built using Spec-Driven Development for Panaversity Hackathon II.

## Project Purpose

This project is an **INTERMEDIATE level command-line todo application** built entirely through spec-driven development. The primary goals are:

1. **Demonstrate Spec-Driven Development**: All code is generated by Claude Code from specifications. No manual coding is permitted.
2. **Phase I INTERMEDIATE**: Upgrade from BASIC (5 features) to INTERMEDIATE (10 features).
3. **In-Memory Python Console App**: A single-file Python application that manages tasks with priority, tags, search, filter, and sort capabilities.
4. **Hackathon**: Panaversity Hackathon II, Phase I.

**Success Criteria**: A fully functional todo application with 10 features: Add, View, Update, Delete, Toggle Status, Set Priority, Manage Tags, Search, Filter, and Sort tasks through a menu-driven interface.

## Core Principles

### I. Simplicity First

Every decision MUST favor the simplest solution that meets requirements.

- No premature optimization
- No features beyond the current phase requirements
- No abstractions until proven necessary by repetition (Rule of Three)
- YAGNI (You Aren't Gonna Need It) applies to all design decisions
- When in doubt, leave it out

**Rationale**: Phase I focuses on proving the concept. Complexity can be added in later phases.

### II. Code Quality Standards

All generated code MUST meet professional quality standards.

- Type hints MUST be present on ALL function parameters and return types
- Docstrings MUST be present on ALL functions using Google format
- Line length MUST NOT exceed 88 characters (Black formatter default)
- Variable names MUST be descriptive and self-documenting
- Magic numbers MUST be extracted to named constants
- Dead code MUST NOT exist in the final implementation
- Function size MUST NOT exceed 50 lines

**Rationale**: High-quality code is easier to maintain, extend, and debug in later phases.

### III. User Experience

The command-line interface MUST be intuitive and helpful.

- Commands MUST use clear, memorable names
- Help text MUST be available and comprehensive
- Error messages MUST explain what went wrong AND how to fix it
- Output MUST be consistently formatted and readable
- User input MUST be forgiving (trim whitespace, handle case variations)
- Confirmation messages MUST be provided for destructive actions
- Priority MUST display with color coding (High=Red, Medium=Yellow, Low=Green)
- Status MUST display with symbols (○ incomplete, ✓ complete)

**Rationale**: A good user experience increases adoption and reduces user frustration.

### IV. Data Integrity

Task data MUST remain consistent and valid at all times.

- Task IDs MUST be unique and never reused within a session
- Task titles MUST NOT be empty or whitespace-only
- Task status MUST only be one of the defined valid states
- Task priority MUST only be "high", "medium", or "low"
- Task tags MUST be unique per task (no duplicates)
- All data modifications MUST validate input before applying changes
- Failed operations MUST NOT corrupt existing data

**Rationale**: Users trust the application with their task data; that trust must be honored.

### V. Explicit Over Implicit

Code behavior MUST be obvious from reading the code.

- No hidden side effects in functions
- No implicit type conversions that change meaning
- All state changes MUST be explicit and traceable
- Function names MUST clearly describe what they do
- No "clever" code that requires deep analysis to understand

**Rationale**: Explicit code is maintainable code.

### VI. Fail Fast and Clearly

Errors MUST be detected early and reported clearly.

- Invalid input MUST be rejected at the entry point
- Error messages MUST include context about what was being attempted
- Stack traces MUST NOT be shown to users (log them if needed)
- Recovery instructions MUST be provided where applicable
- Silent failures are FORBIDDEN
- Errors display in red (ANSI code), success in green (ANSI code)

**Rationale**: Early, clear failures prevent cascading problems and aid debugging.

### VII. Functional Style Preferred

Prefer pure functions and immutable data patterns.

- Functions SHOULD be pure where practical (same input = same output)
- Data SHOULD be passed explicitly, not accessed via globals
- State mutations SHOULD be isolated and minimal
- Side effects SHOULD be pushed to the edges of the system
- Sort operations MUST return new lists (not mutate originals)
- Filter operations MUST return new lists (not mutate originals)

**Rationale**: Functional patterns reduce bugs and make testing easier.

### VIII. Separation of Concerns

Each layer of the application has a single responsibility.

- **Data Layer**: Manages task storage, retrieval, and data operations (add, get, delete, set_priority, add_tag, remove_tag, search, filter, sort)
- **Validation Layer**: Validates all input and business rules (title, description, ID, priority, tag)
- **Display Layer**: Formats output for the user (tables, colors, symbols)
- **Command Layer**: Parses user input and orchestrates operations (cmd_* functions)
- **Application Layer**: Main loop and menu handling

Functions MUST NOT cross layer boundaries inappropriately.

**Rationale**: Clear separation makes the codebase navigable and testable.

### IX. Testability

All code MUST be designed to be testable.

- Functions MUST be small enough to test in isolation
- Dependencies MUST be injectable where needed
- Pure functions MUST be preferred for business logic
- State MUST be explicit and inspectable
- Edge cases MUST be handleable and testable

**Rationale**: Testable code is reliable code.

### X. Backward Compatibility

All BASIC level features MUST continue to work unchanged.

- Menu options 1-5 MUST behave identically to BASIC level
- Existing data model fields MUST remain unchanged
- New tasks MUST have default values: priority="medium", tags=[]
- New features (options 6-10) MUST be additive, not breaking

**Rationale**: Upgrading should enhance, not break existing functionality.

### Error Handling

**Pattern for functions that can fail**:

```python
# ✅ CORRECT - Tuple return pattern
def validate_tag(tag: str) -> tuple[bool, str]:
    """Validate a tag value.

    Returns:
        (True, normalized_tag) on success.
        (False, error_message) on failure.
    """
    cleaned = tag.strip().lower()
    if not cleaned:
        return False, "Error: Tag cannot be empty."
    if len(cleaned) > 20:
        return False, "Error: Tag must be 1-20 characters."
    if not all(c.isalnum() or c == '-' for c in cleaned):
        return False, "Error: Tag must be alphanumeric and hyphens only."
    return True, cleaned
```

**FORBIDDEN**:
- Bare `except:` clauses
- Catching `Exception` without re-raising
- Silent error swallowing
- Returning `None` to indicate failure (use tuple pattern instead)

## Architectural Patterns

### Layer Architecture (5 Layers)

```
┌─────────────────────────────────────┐
│      Application Layer (main)       │  ← Main loop, menu handling
├─────────────────────────────────────┤
│      Command Layer (cmd_*)          │  ← Parses input, orchestrates
├─────────────────────────────────────┤
│    Validation Layer (validate_*)    │  ← Validates input, returns errors
├─────────────────────────────────────┤
│       Data Layer (CRUD + ops)       │  ← Storage, search, filter, sort
├─────────────────────────────────────┤
│      Display Layer (display_*)      │  ← Formats output, colors
└─────────────────────────────────────┘
```

### Data Flow

1. User enters command → Application Layer shows menu
2. User selects option → Command Layer receives input
3. Command Layer calls Validation Layer to validate input
4. If validation fails, Display Layer shows error
5. If validation passes, Command Layer calls Data Layer
6. Data Layer performs operation, returns result
7. Display Layer shows result to user

### State Management

- The task list is a `list[dict]` passed explicitly to all functions
- No global variables for state
- The main loop owns the task list and passes it to functions
- Functions MUST NOT modify the list directly for search/filter/sort; they return new data

## Validation Rules

### Priority Validation

```python
def validate_priority(priority: str) -> tuple[bool, str]:
    """Validate priority value.

    Rules:
    - Must be exactly "high", "medium", or "low"
    - Case-insensitive input (convert to lowercase)
    - Whitespace trimmed

    Returns:
        (True, normalized_priority) on success.
        (False, "Error: Priority must be high, medium, or low") on failure.
    """
```

**Examples**:
```python
# ✅ Valid priorities
validate_priority("high")      # → (True, "high")
validate_priority("HIGH")      # → (True, "high")
validate_priority("  Medium ") # → (True, "medium")
validate_priority("low")       # → (True, "low")

# ❌ Invalid priorities
validate_priority("")          # → (False, "Error: Priority must be high, medium, or low")
validate_priority("urgent")    # → (False, "Error: Priority must be high, medium, or low")
validate_priority("1")         # → (False, "Error: Priority must be high, medium, or low")
```

### Tag Validation

```python
def validate_tag(tag: str) -> tuple[bool, str]:
    """Validate a tag value.

    Rules:
    - Length: 1-20 characters
    - Allowed characters: alphanumeric (a-z, A-Z, 0-9) and hyphens (-)
    - No spaces, no special characters except hyphen
    - Converted to lowercase
    - Whitespace trimmed

    Returns:
        (True, normalized_tag) on success.
        (False, error_message) on failure.
    """
```

**Examples**:
```python
# ✅ Valid tags
validate_tag("work")           # → (True, "work")
validate_tag("URGENT")         # → (True, "urgent")
validate_tag("phase-1")        # → (True, "phase-1")
validate_tag("todo123")        # → (True, "todo123")

# ❌ Invalid tags
validate_tag("")               # → (False, "Error: Tag cannot be empty.")
validate_tag("   ")            # → (False, "Error: Tag cannot be empty.")
validate_tag("a" * 21)         # → (False, "Error: Tag must be 1-20 characters.")
validate_tag("has space")      # → (False, "Error: Tag must be alphanumeric and hyphens only.")
validate_tag("has@symbol")     # → (False, "Error: Tag must be alphanumeric and hyphens only.")
```

### Priority Display Function

```python
def display_priority_with_color(priority: str) -> str:
    """Format priority with appropriate ANSI color.

    Args:
        priority: The priority value (high, medium, low).

    Returns:
        Colored priority string for terminal display.
    """
    if priority == PRIORITY_HIGH:
        return f"{COLOR_RED}{priority.upper()}{COLOR_RESET}"
    elif priority == PRIORITY_MEDIUM:
        return f"{COLOR_YELLOW}{priority}{COLOR_RESET}"
    else:
        return f"{COLOR_GREEN}{priority}{COLOR_RESET}"
```

    Returns:

    Returns:
        New list containing matching tasks (does not mutate original).

def filter_tasks(

    priority: str | None = None,

        priority: Filter by priority ("high"/"medium"/"low") or None for any.
        tag: Filter by tag or None for any.

    Returns:
        New list containing matching tasks (does not mutate original).
    """

    tasks: list[dict],
    key: str,
    reverse: bool = False

    """Sort tasks by a specified key.

    Args:
        tasks: The list of task dictionaries to sort.
        key: Sort key - "date" (created_at), "priority", or "title".
        reverse: If True, sort in descending order.

    Returns:
        New sorted list (does not mutate original).
    """
