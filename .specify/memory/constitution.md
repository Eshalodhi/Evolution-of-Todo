# TODO App Constitution

A command-line todo application built using Spec-Driven Development for a hackathon.

## Project Purpose

This project is a **command-line todo application** built entirely through spec-driven development. The primary goals are:

1. **Demonstrate Spec-Driven Development**: All code is generated by Claude Code from specifications. No manual coding is permitted.
2. **Phase I Simplicity**: This is Phase I of a 5-phase hackathon. The focus is on a minimal, working implementation.
3. **In-Memory Python Console App**: A simple, single-file Python application that manages tasks in memory.

**Success Criteria**: A fully functional todo application where users can add, list, complete, and delete tasks through a command-line interface.

## Core Principles

### I. Simplicity First

Every decision MUST favor the simplest solution that meets requirements.

- No premature optimization
- No features beyond the current phase requirements
- No abstractions until proven necessary by repetition (Rule of Three)
- YAGNI (You Aren't Gonna Need It) applies to all design decisions
- When in doubt, leave it out

**Rationale**: Phase I focuses on proving the concept. Complexity can be added in later phases.

### II. Code Quality Standards

All generated code MUST meet professional quality standards.

- Type hints MUST be present on ALL function parameters and return types
- Docstrings MUST be present on ALL functions using Google format
- Line length MUST NOT exceed 88 characters (Black formatter default)
- Variable names MUST be descriptive and self-documenting
- Magic numbers MUST be extracted to named constants
- Dead code MUST NOT exist in the final implementation

**Rationale**: High-quality code is easier to maintain, extend, and debug in later phases.

### III. User Experience

The command-line interface MUST be intuitive and helpful.

- Commands MUST use clear, memorable names
- Help text MUST be available and comprehensive
- Error messages MUST explain what went wrong AND how to fix it
- Output MUST be consistently formatted and readable
- User input MUST be forgiving (trim whitespace, handle case variations)
- Confirmation messages MUST be provided for destructive actions

**Rationale**: A good user experience increases adoption and reduces user frustration.

### IV. Data Integrity

Task data MUST remain consistent and valid at all times.

- Task IDs MUST be unique and never reused within a session
- Task descriptions MUST NOT be empty or whitespace-only
- Task status MUST only be one of the defined valid states
- All data modifications MUST validate input before applying changes
- Failed operations MUST NOT corrupt existing data

**Rationale**: Users trust the application with their task data; that trust must be honored.

### V. Explicit Over Implicit

Code behavior MUST be obvious from reading the code.

- No hidden side effects in functions
- No implicit type conversions that change meaning
- All state changes MUST be explicit and traceable
- Function names MUST clearly describe what they do
- No "clever" code that requires deep analysis to understand

**Rationale**: Explicit code is maintainable code.

### VI. Fail Fast and Clearly

Errors MUST be detected early and reported clearly.

- Invalid input MUST be rejected at the entry point
- Error messages MUST include context about what was being attempted
- Stack traces MUST NOT be shown to users (log them if needed)
- Recovery instructions MUST be provided where applicable
- Silent failures are FORBIDDEN

**Rationale**: Early, clear failures prevent cascading problems and aid debugging.

### VII. Functional Style Preferred

Prefer pure functions and immutable data patterns.

- Functions SHOULD be pure where practical (same input = same output)
- Data SHOULD be passed explicitly, not accessed via globals
- State mutations SHOULD be isolated and minimal
- Side effects SHOULD be pushed to the edges of the system
- Prefer returning new data over mutating existing data

**Rationale**: Functional patterns reduce bugs and make testing easier.

### VIII. Separation of Concerns

Each layer of the application has a single responsibility.

- **Data Layer**: Manages task storage and retrieval
- **Validation Layer**: Validates all input and business rules
- **Display Layer**: Formats output for the user
- **Command Layer**: Parses user input and orchestrates operations

Functions MUST NOT cross layer boundaries inappropriately.

**Rationale**: Clear separation makes the codebase navigable and testable.

### IX. Testability

All code MUST be designed to be testable.

- Functions MUST be small enough to test in isolation
- Dependencies MUST be injectable where needed
- Pure functions MUST be preferred for business logic
- State MUST be explicit and inspectable
- Edge cases MUST be handleable and testable

**Rationale**: Testable code is reliable code.

## Technical Constraints

These constraints are NON-NEGOTIABLE for Phase I.

### Language and Runtime

| Constraint | Value | Rationale |
|------------|-------|-----------|
| Python Version | 3.13+ | Latest stable version with best type hint support |
| External Dependencies | NONE | Standard library only; no pip install required |
| Implementation | Single file | `todo.py` contains all code |
| Storage | In-memory only | No database, no file I/O, no persistence |
| Platform | Cross-platform | Must work on Windows, macOS, Linux |

### Forbidden Patterns

The following are explicitly FORBIDDEN:

- `import` of any non-standard library module
- File I/O operations (open, read, write)
- Network operations
- Database connections
- Global mutable state (except the task list passed as parameter)
- Threading or async operations
- External process execution
- Environment variable dependencies for configuration

## Architectural Patterns

### Layer Architecture

```
┌─────────────────────────────────────┐
│         Command Layer (cmd_*)       │  ← Parses input, calls other layers
├─────────────────────────────────────┤
│       Validation Layer (validate_*) │  ← Validates input, returns errors
├─────────────────────────────────────┤
│         Data Layer (get_*, add_*)   │  ← CRUD operations on tasks
├─────────────────────────────────────┤
│        Display Layer (display_*)    │  ← Formats output for user
└─────────────────────────────────────┘
```

### Data Flow

1. User enters command → Command Layer parses it
2. Command Layer calls Validation Layer to validate input
3. If validation fails, Display Layer shows error
4. If validation passes, Command Layer calls Data Layer
5. Data Layer performs operation, returns result
6. Display Layer shows result to user

### State Management

- The task list is a `list[dict]` passed explicitly to all functions
- No global variables for state
- The main loop owns the task list and passes it to functions
- Functions MUST NOT modify the list directly; they return new data or use explicit mutation

## Error Handling Strategy

### Input Validation

All user input MUST be validated before processing:

1. **Type validation**: Ensure correct type (e.g., task_id is numeric)
2. **Range validation**: Ensure values are within bounds (e.g., description length)
3. **Format validation**: Ensure correct format (e.g., non-empty after trim)
4. **Existence validation**: Ensure referenced entities exist (e.g., task ID exists)

### Error Message Format

Error messages MUST follow this pattern:

```
Error: [What went wrong]. [How to fix it].
```

Examples:
- `Error: Task ID must be a number. Please enter a valid task ID like 'done 1'.`
- `Error: Task 5 not found. Use 'list' to see available tasks.`
- `Error: Description cannot be empty. Please provide a description for your task.`

### Return Value Pattern

Functions that can fail MUST return `tuple[bool, str]`:

```python
def validate_description(description: str) -> tuple[bool, str]:
    """Validate a task description.

    Returns:
        (True, cleaned_description) on success.
        (False, error_message) on failure.
    """
    cleaned = description.strip()
    if not cleaned:
        return False, "Error: Description cannot be empty."
    if len(cleaned) > 200:
        return False, f"Error: Description too long ({len(cleaned)} chars). Maximum is 200."
    return True, cleaned
```

## Non-Negotiables

These requirements MUST be met in every code review. Violations result in rejection.

### Absolute Requirements

1. **Type hints on ALL functions** - No exceptions
2. **Docstrings on ALL functions** - Google format, no exceptions
3. **No bare except clauses** - Always catch specific exceptions
4. **No global mutable state** - Pass state explicitly
5. **No external dependencies** - Standard library only
6. **Single file implementation** - All code in `todo.py`
7. **Error messages include remediation** - Tell user how to fix
8. **Line length ≤ 88 characters** - Black formatter default
9. **No dead code** - Every line must be reachable and necessary
10. **No magic numbers** - Use named constants

### Code Review Checklist

Before any code is accepted:

- [ ] All functions have type hints
- [ ] All functions have Google-format docstrings
- [ ] No bare `except:` clauses
- [ ] No global variables for state
- [ ] No imports outside standard library
- [ ] All code in single `todo.py` file
- [ ] All error messages are user-friendly
- [ ] All lines ≤ 88 characters
- [ ] No unused code or imports
- [ ] All magic numbers are named constants
